# Requirements Document

## Introduction

Smart Ticket Allocation is a feature in the Jira Sprint Dashboard that enables team leads to define which projects each assignee is eligible to work on, then automatically suggest assignments for unassigned tickets in the current sprint based on eligibility and remaining capacity. All allocation work happens entirely within the dashboard tab — no changes are written back to Jira. The user reviews suggestions and makes final assignments manually in Jira. The feature integrates as a new tab in the existing dashboard.

## Glossary

- **Allocation_Tab**: The new dashboard tab that hosts the Smart Ticket Allocation UI
- **Assignee**: A team member visible in the dashboard's active data
- **Eligibility**: The set of Jira project keys an Assignee is permitted to work on
- **Eligibility_Config**: The persisted mapping of Assignee → eligible project keys, stored in localStorage
- **Unassigned_Ticket**: A Jira issue in the active sprint whose assignee field is null or empty
- **Remaining_Capacity**: An Assignee's sprint capacity (story points) minus the story points already assigned to them in the active sprint
- **Suggestion**: A recommended pairing of one Unassigned_Ticket to one Assignee, generated by the Suggestion_Engine
- **Suggestion_Engine**: The algorithm that matches Unassigned_Tickets to Assignees based on Eligibility and Remaining_Capacity
- **Active_Sprint**: The sprint currently selected in the dashboard sprint filter
- **Capacity_Tab**: The existing Capacity tab in the dashboard that tracks per-assignee story point capacity
- **Ticket_Pool**: The set of Unassigned_Tickets from projects an Assignee is eligible for

## Requirements

### Requirement 1: Eligibility Configuration

**User Story:** As a team lead, I want to define which projects each assignee is eligible to work on, so that suggestions are only made for appropriate pairings.

#### Acceptance Criteria

1. THE Allocation_Tab SHALL display a list of all Assignees sourced from the dashboard's active data
2. WHEN an Assignee row is expanded, THE Allocation_Tab SHALL display a multi-select list of all project keys present in the active sprint data
3. WHEN the user toggles a project key for an Assignee, THE Allocation_Tab SHALL update the Eligibility_Config for that Assignee within 100ms
4. THE Allocation_Tab SHALL persist Eligibility_Config to localStorage under the key `assigneeEligibility`
5. WHEN the Allocation_Tab loads, THE Allocation_Tab SHALL restore Eligibility_Config from localStorage if a saved value exists
6. THE Allocation_Tab SHALL display each Assignee's eligible project keys as compact tags in the collapsed row view
7. WHERE CC and WTR1 project keys are present in the sprint data, THE Allocation_Tab SHALL pre-select them as eligible for all Assignees on first load when no saved Eligibility_Config exists

### Requirement 2: Unassigned Ticket Pool

**User Story:** As a team lead, I want to see all unassigned tickets in the current sprint, so that I know what needs to be allocated.

#### Acceptance Criteria

1. THE Allocation_Tab SHALL display a list of all Unassigned_Tickets from the Active_Sprint
2. WHEN the Active_Sprint filter changes, THE Allocation_Tab SHALL refresh the Unassigned_Ticket list within 200ms
3. THE Allocation_Tab SHALL display for each Unassigned_Ticket: issue key, summary, project key, issue type, and story points
4. THE Allocation_Tab SHALL display a count of total Unassigned_Tickets at the top of the list
5. IF the Active_Sprint contains no Unassigned_Tickets, THEN THE Allocation_Tab SHALL display a message indicating all tickets are assigned
6. WHEN an Assignee's Eligibility_Config is updated to include a new project key, THE Allocation_Tab SHALL immediately reflect any newly eligible Unassigned_Tickets in that Assignee's visible Ticket_Pool without requiring a page reload

### Requirement 3: Suggestion Engine

**User Story:** As a team lead, I want the system to automatically suggest who should be assigned each unassigned ticket, so that I can allocate work quickly without manual analysis.

#### Acceptance Criteria

1. WHEN the user clicks "Generate Suggestions", THE Suggestion_Engine SHALL compute a Suggestion for each Unassigned_Ticket
2. THE Suggestion_Engine SHALL only suggest an Assignee for a ticket if the ticket's project key is in that Assignee's Eligibility_Config
3. THE Suggestion_Engine SHALL only suggest an Assignee whose Remaining_Capacity is greater than or equal to the ticket's story points
4. WHEN multiple eligible Assignees exist for a ticket, THE Suggestion_Engine SHALL select the Assignee with the highest Remaining_Capacity
5. WHEN no eligible Assignee has sufficient Remaining_Capacity for a ticket, THE Suggestion_Engine SHALL mark that ticket as "No Suggestion Available"
6. THE Suggestion_Engine SHALL update Remaining_Capacity after each Suggestion is generated, so that subsequent suggestions reflect already-allocated work
7. THE Suggestion_Engine SHALL complete all suggestions within 500ms for datasets containing up to 500 Unassigned_Tickets
8. WHEN a ticket has 0 story points, THE Suggestion_Engine SHALL treat it as requiring 1 story point for capacity comparison purposes

### Requirement 4: Drag-and-Drop Allocation and Manual Adjustment

**User Story:** As a team lead, I want to drag tickets freely between assignees and from the unassigned pool, so that I have full visual control over the allocation plan before actioning it in Jira.

#### Acceptance Criteria

1. THE Allocation_Tab SHALL display each Assignee as a swimlane/column showing their name, eligible project tags, remaining capacity, and their currently allocated tickets
2. THE Allocation_Tab SHALL display a separate Unassigned pool column containing all Unassigned_Tickets from the Active_Sprint
3. WHEN the user drags a ticket from the Unassigned pool onto an Assignee column, THE Allocation_Tab SHALL move that ticket into the Assignee's allocated list, provided the Assignee is eligible for that ticket's project
4. WHEN the user drags an already-allocated ticket from one Assignee column onto a different Assignee column, THE Allocation_Tab SHALL move the ticket to the new Assignee, provided the new Assignee is eligible for that ticket's project
5. WHEN a ticket is dragged back onto the Unassigned pool column, THE Allocation_Tab SHALL return it to unassigned status and restore the previous Assignee's Remaining_Capacity
6. WHEN a ticket is dragged onto an ineligible Assignee, THE Allocation_Tab SHALL reject the drop and show a brief visual indicator (e.g. red highlight) explaining the ticket's project is not in that Assignee's eligibility
7. DURING a drag operation, THE Allocation_Tab SHALL highlight valid drop targets in green and invalid drop targets in red so the user can see at a glance where a ticket can land
8. THE Allocation_Tab SHALL display each Suggestion (from the Suggestion_Engine) as a pre-populated allocation within the relevant Assignee column, which the user can then adjust via drag-and-drop
9. WHEN a Suggestion is displayed, THE Allocation_Tab SHALL also allow the user to change the suggested Assignee via a dropdown containing only eligible Assignees for that ticket's project
10. THE Allocation_Tab SHALL display the full allocation plan (all current allocations across all Assignee columns) in a copyable summary so the user can action them manually in Jira

### Requirement 5: Capacity Visibility

**User Story:** As a team lead, I want to see each assignee's current capacity alongside the suggestions, so that I can make informed allocation decisions.

#### Acceptance Criteria

1. THE Allocation_Tab SHALL display each Assignee's total sprint capacity and Remaining_Capacity in the assignee list
2. WHEN a Suggestion is added or dismissed, THE Allocation_Tab SHALL update the displayed Remaining_Capacity for the affected Assignee within 100ms
3. WHEN an Assignee's Remaining_Capacity reaches zero, THE Allocation_Tab SHALL visually indicate that the Assignee is at full capacity
4. THE Allocation_Tab SHALL source sprint capacity values from the same data used by the existing Capacity_Tab

### Requirement 6: Integration with Existing Dashboard

**User Story:** As a team lead, I want the allocation feature to feel like a natural part of the dashboard, so that I don't need to switch between tools.

#### Acceptance Criteria

1. THE Allocation_Tab SHALL appear as a tab in the main dashboard navigation
2. THE Allocation_Tab SHALL use the existing dark theme design tokens for all colors, spacing, and typography
3. THE Allocation_Tab SHALL read sprint and ticket data from the same `cachedDashboardData` localStorage key used by the rest of the dashboard
4. WHEN the dashboard sprint filter changes, THE Allocation_Tab SHALL reflect the new Active_Sprint without requiring a page reload
5. THE Allocation_Tab SHALL make no external API calls at any point — all data comes from the dashboard's in-memory state

## Correctness Properties

### Property 1: Eligibility Constraint (Invariant)

FOR ALL generated Suggestions:
- The suggested Assignee's Eligibility_Config SHALL contain the ticket's project key
- No Suggestion SHALL pair a ticket with an Assignee who is not eligible for that project

### Property 2: Capacity Constraint (Invariant)

FOR ALL generated Suggestions at the time of generation:
- The suggested Assignee's Remaining_Capacity SHALL be greater than or equal to the ticket's story points (treating 0 SP tickets as 1 SP)
- No Suggestion SHALL cause an Assignee's total allocated story points to exceed their sprint capacity

### Property 3: Suggestion Engine Idempotence

FOR ALL identical inputs (same Unassigned_Tickets, same Eligibility_Config, same Remaining_Capacity values):
- Running the Suggestion_Engine twice SHALL produce identical Suggestion sets
- The order of Suggestions SHALL be deterministic

### Property 4: Capacity Deduction Consistency (Invariant)

FOR ALL sequences of Suggestion generation:
- The sum of story points across all Suggestions for a given Assignee SHALL equal the reduction in that Assignee's Remaining_Capacity
- Remaining_Capacity SHALL never go below zero as a result of Suggestion generation

### Property 5: Eligibility Config Round-Trip

FOR ALL valid Eligibility_Config states:
- Saving to localStorage then restoring SHALL produce an identical Eligibility_Config
- All Assignee → project key mappings SHALL be preserved exactly

### Property 6: No Suggestion for Fully Allocated Assignees (Invariant)

FOR ALL Assignees where Remaining_Capacity equals zero:
- THE Suggestion_Engine SHALL not generate any Suggestion targeting that Assignee
- This property SHALL hold regardless of the Assignee's Eligibility_Config
